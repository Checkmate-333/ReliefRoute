Problem & solution
The problem

Disaster relief is often a black box.

  • • Donors send money or materials, but rarely see where their help actually ends up.
  • • NGOs juggle spreadsheets, WhatsApp groups and manual logs – easy to lose track.
  • • Relief kits can be delayed, duplicated or even diverted before reaching survivors.
  • • Governments struggle to audit who received what, and which regions are under-served.
Opaque flows Low trust Inefficient allocation
Our solution

ReliefRail – per-packet, on-chain visibility.

  • ✔ Every physical kit gets a unique digital identity (ID / token) on a blockchain.
  • ✔ Volunteers scan QR codes at each checkpoint to update status: packed, in transit, delivered.
  • ✔ All status changes are stored as immutable on-chain events – no silent edits.
  • ✔ Donors see the journey of kits they funded; NGOs and authorities see a live distribution map.
Per-kit tracking Shared source of truth Audit-ready logs
Flow

How ReliefRail works, step by step.

A simple 5-stage flow that matches real-world disaster operations but adds transparent, decentralized tracking.

1
NGO admin
Create batch & mint kits

The NGO creates a relief batch (e.g., “Odisha floods”) and specifies the number of kits, contents and target region. Each kit gets a unique on-chain ID.

2
System
Generate & stick QR codes

ReliefRail generates QR labels linked to each kit ID. These are printed and stuck on physical packets at the warehouse.

3
Volunteers
Scan at every checkpoint

At each hand-off (warehouse, truck, local depot, field), volunteers scan QR codes using a mobile-friendly web app and update status + location.

4
Blockchain
Write immutable status events

Every status change emits an event on an EVM chain (e.g., Polygon). Logs cannot be silently modified or deleted later.

5
Dashboards
Donor & NGO insights

Donors see the journey of their funded kits, NGOs see bottlenecks and coverage, and auditors get end-to-end traceability.

Key modules

Core components we plan to implement.

  • • ReliefRailRegistry.sol – stores kit metadata and emits status update events.
  • • REST backend – handles role-based actions, talks to contracts via ethers.js / sponsor SDKs.
  • • NGO admin UI – create batches, mint kits, download QR sheets, monitor deliveries.
  • • Volunteer scanner UI – lightweight mobile web app for scanning QRs and pushing status + location.
  • • Donor dashboard – list of funded kits, with their latest status and location pins on a map.

Demo flow

How we’ll present ReliefRail to judges.

A crisp 3–5 minute walkthrough that connects the human story with the technical execution.

1. Scenario setup A flood hits a district. An NGO wants to send 100 relief kits, funded by online donors.
2. NGO dashboard Show batch creation, minting of kits and generation of QR codes for printing.
3. Volunteer scan Simulate scanning a kit and updating it from “Packed” → “In transit” → “Delivered”.
4. Donor view Switch to donor dashboard, show 2 kits delivered, 1 kit in transit, plus a simple map.
5. On-chain proof Show a transaction / event log in a block explorer, reinforcing that no log entries can be quietly edited.

Closing line: “ReliefRail makes disaster aid as trackable as an online order – but with lives on the other end.”
